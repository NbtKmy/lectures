## 1. 目的

名古屋市守山区を対象に、オープンデータとQGISを利用して**徒歩による医療アクセス**を可視化・集計できることを示す。

- **分析A：病院中心** — 各病院の徒歩10・20・30分圏内に何人住んでいるか。
- **分析B：住民中心** — 守山区の住民の何％が、徒歩10・20・30分以内に少なくとも1つの病院へ到達できるか。

両分析では、病院地点・徒歩道路網・時間圏の生成までの処理を共通化できる。一方で、人口集計の目的・対象地域・重複の扱いが異なる。

| 項目 | 分析A：病院中心 | 分析B：住民中心 |
|---|---|---|
| 主な問い | 個々の病院の徒歩圏内人口 | 守山区民の徒歩アクセス率 |
| 対象病院 | 評価対象として選んだ病院 | 区外も含む周辺の病院 |
| 時間圏 | 病院ごとに保持 | 同じ時間閾値の時間圏を統合 |
| 人口集計 | 区外住民も対象にし得る | 守山区民のみ |
| 重複 | 同一住民が複数病院に計上され得る | 同一住民を二重計上しない |

**デモのメッセージ：** QGISではGUIによって空間データを確認・加工・分析できるが、研究上の問いに応じて分析単位・集計範囲・仮定を設計する必要がある。

### 作業用座標系（CRS）

**EPSG:6675 = JGD2011 / Japan Plane Rectangular CS VII（平面直角座標系第VII系）** を作業用とする。愛知県を対象とする距離・面積分析に適した、単位がメートルの投影座標系。

- プロジェクト右下のCRS表示からプロジェクトCRSを設定。
- 元レイヤの座標系が別の場合は、レイヤを右クリック → **エクスポート → 地物の保存…** で出力CRSをEPSG:6675にして再投影する。
- **注意：** 単にレイヤのCRSを「指定」し直すのと、座標値を変換する**再投影**は異なる。元データの座標系を誤って上書きしないこと。
- e-Statで取得した「世界測地系・平面直角座標系」の正確なEPSGコードは、読み込み後に **レイヤプロパティ → 情報／ソース** で確認する。

## 3. 実施した作業とQGIS操作

### 3.1 OpenStreetMapのXYZタイルを表示

1. QGISの**ブラウザ**パネルで **XYZ Tiles** を展開。
2. `OpenStreetMap` をダブルクリック（またはキャンバスへドラッグ）。
3. 背景地図として表示。

> XYZタイルは画像としての背景地図。経路計算には使えないため、後で**ベクタ形式のOSM道路ネットワーク**を別途用意する。

### 3.2 守山区の行政境界と病院ポイントを読み込む

1. 取得した行政区域データと病院ポイントをQGISへ追加。
2. 守山区の境界を表示し、病院ポイントの位置と範囲を確認。
3. プロジェクトの作業用CRSをEPSG:6675に設定。

**今後の確認：** 病院データが「病院」「一般診療所」「歯科診療所」を含む場合は、研究上の定義に沿って対象施設を抽出する。施設の開設状況、位置（建物中心か入口か）も確認する。

### 3.3 人口統計CSVと250mメッシュ境界を入手

1. e-Statから人口統計CSV `tblT001142Q23.csv` を取得。
2. 5次（250m）メッシュ境界を取得。守山区は**`MESH05236` と `MESH05237`** にまたがるため、両方取得。
3. ZIPを展開。Shapefileの場合は `.shp`、`.shx`、`.dbf`、`.prj` を同じフォルダに保つ。
4. 2つの境界レイヤをQGISへ読み込む。

**CSVの確認事項（実ファイルで確認済み）：**

- 文字コード：**CP932（Shift_JIS系）**。
- 1行目：`KEY_CODE`、`T001142001` 等の英数字フィールド名。
- **2行目：項目の日本語説明**（通常のデータ行ではない）。3行目からメッシュのデータ。
- `KEY_CODE`：10桁の250mメッシュコード。**文字列として保持**する。
- `T001142001`：総人口。後で数値型 `population` に変換。
- `HTKSYORI`、`HTKSAKI`、`GASSAN`：秘匿・合算処理に関係する項目。

QGISでは **レイヤ → レイヤを追加 → CSVテキストレイヤを追加**（Delimited Text）から、区切り文字をカンマ、ジオメトリを「なし」にして読み込める。2行目の説明行を誤って通常レコードとして扱わないよう注意する。必要ならコピーしたCSVから説明行だけを除いた作業用CSVを作る（原本は保持）。

### 3.4 2つの250mメッシュ境界をマージ

**プロセシングツールボックス → ベクタレイヤをマージ（Merge Vector Layers）**

| パラメータ | 設定 |
|---|---|
| 入力レイヤ | `MESH05236`、`MESH05237` のメッシュ境界 |
| 出力CRS | EPSG:6675（必要に応じて事前に各レイヤを再投影） |
| 出力 | 例：`moriyama_mesh.gpkg` |

- **マージ**は2レイヤの地物を1レイヤにまとめる処理。区画の境界を消す**ディゾルブ（融合）**とは異なる。
- 出力属性に `KEY_CODE` が残っていることと、重複コードがないことを確認。
- 当初、マージ後は約**201,600件**のメッシュがあり、守山区外を広く含んだ。

### 3.5 守山区の周辺3kmバッファを作る

**プロセシングツールボックス → バッファ（Buffer）**

| パラメータ | 設定 |
|---|---|
| 入力レイヤ | 守山区の行政境界 |
| 距離 | `3000`（EPSG:6675なら単位はm） |
| 出力 | 例：`moriyama_buffer_3km.gpkg` |

このバッファは、**区外の病院・住民・道路も後続分析に含められるようにするための作業範囲**。行政界そのものや最終的な徒歩圏とは別物。

### 3.6 人口CSVとメッシュ境界を結合

結合キーは双方の **`KEY_CODE`**。

**QGIS操作：**

1. メッシュレイヤを右クリック → **プロパティ → 結合（Joins）** → `＋`。
2. **結合レイヤ：** 人口CSV。
3. **結合フィールド：** CSV側 `KEY_CODE`。
4. **ターゲットフィールド：** メッシュ側 `KEY_CODE`。
5. 属性テーブルで総人口 `T001142001` が見えるか確認。
6. 必要なレイヤを右クリック → **エクスポート → 地物の保存…** → **GeoPackage** に保存し、結合結果を実体化。

**実際の試行錯誤：** 当初は広域の約20万メッシュを人口CSVと結合し、GeoPackageとして保存した。その後フィルター操作でQGISが長時間応答しなくなった。再起動後、結合済みGeoPackageを維持して、次の「場所による抽出」で範囲を縮小した。**今後同じ作業をやり直すなら、先に空間抽出してから人口CSVを結合する方が軽量で推奨。**

### 3.7 守山区＋周辺3kmのメッシュを抽出

**プロセシングツールボックス → 場所による抽出（Extract by Location）**

| パラメータ | 設定 |
|---|---|
| 入力レイヤ | 結合済み `moriyama_mesh`（GeoPackage） |
| 空間条件 | `intersects`（交差） |
| 比較レイヤ | `moriyama_buffer_3km` |
| 出力 | 例：`moriyama_mesh_local.gpkg` |

ここでは元の250mメッシュの形を**切らずに抽出**する。元面積が後の人口按分に必要なため。大きいレイヤは非表示にし、以後は小さいレイヤで作業する。

> メモの整理上は「抽出 → 人口結合」の順が理想的だが、**今回実際に行ったのは「広域メッシュに結合してGeoPackage保存 → 抽出」**。両者を混同しない。

### 3.8 総人口を文字列から数値型へ変換

CSV由来の総人口値が文字列として読み込まれていたため、新しい数値フィールドを作成した。

**QGIS操作：** `moriyama_mesh_local` の属性テーブル → **フィールド計算機（Field Calculator）**。

| パラメータ | 設定 |
|---|---|
| 新しいフィールド名 | `population` |
| 出力フィールド型 | 整数（Integer） |
| 式 | 下記（実際のフィールド名に合わせて変更） |

```qgis
 to_int("tblT001142Q23_T001142001")
```

人口が `1,234` のようなカンマ入り文字列なら：

```qgis
 to_int(replace("tblT001142Q23_T001142001", ',', ''))
```

**注意：** `NULL`、秘匿値（例：`*`）、「0」は異なる。変換できない値を無条件にゼロへ置換しない。

### 3.9 人口メッシュを色分け表示

`moriyama_mesh_local` を右クリック → **プロパティ → シンボロジ → Graduated（連続値による定義）**。

1. **値／フィールド：** `population`。
2. 色階調・分類数を指定（例：5段階）。
3. **分類（Classify）**を押して適用。
4. 人口の多い／少ない地域と、表示されないメッシュを地図上で確認。

## 4. 問題・調査結果・注意点

### 4.1 フィルター時にQGISが応答しなくなった

- 広域約201,600件のメッシュに人口属性を結合した状態でフィルターをかけたところ、処理が終わらなくなった。
- QGISを復旧し、結合済みGeoPackageから必要な地域を **Extract by Location** で抽出できた。
- **推奨：** データを早い段階で対象地域に絞る。大規模レイヤへのフィルターや再計算を不用意に繰り返さない。元ファイルとQGISプロジェクトは保存・バックアップする。
- 処理が遅かった原因は未計測であり、結合だけが原因と断定はできない。

### 4.2 人口ゼロ・NULL・「穴」の区別

地図表示で、白い区画と背景地図が見える「穴」を発見した。

- QGISの**地物情報表示（Identify Features）**を使い、白い区画には地物と属性があることを確認。
- 一方、抽出済みレイヤで背景地図が見える位置をクリックしても地物情報が表示されなかった。
- 広域の元メッシュレイヤでは、対応箇所のポリゴンが存在し、`population = NULL` だった。
- 具体例：**`KEY_CODE = 5237608414`**。アップロード済み人口CSVを直接確認したところ、**このコードのレコードはCSV内に存在しなかった**。
- 問題の場所は地図上で公園・山林・河川等と重なっており、非居住地の可能性がある。

**ここから確実に言えるのは「対応する人口データが結合されていない」ことまで。** `NULL` を一律に「人口0人」や「欠損しても影響なし」と決めつけない。人口統計の対象範囲、秘匿・合算処理、行政界をまたぐ範囲を確認する。背景地図が見えた原因が「抽出時に地物が落ちた」のか「表示・NULLフィルター等によるもの」なのかも、必要なら再点検する。

**デモでの扱い：** `population` の元値は保持する。NULLを別扱いで可視化し、人口集計からの除外や仮定を明記する。面積按分の分母を作る際に、0とNULLを混同しない。

### 4.3 統計と行政区域のカバー範囲

250mメッシュ境界は守山区だけではなく広域をカバーし、人口CSVは愛知県の収録範囲に依存する。区外まで人口を計上する**分析A**では、愛知県境を越える時間圏がある場合、隣県の人口データが別途必要になる可能性がある。

## 6. 当初の次回作業計画（2026-11-09時点・履歴として保存）

1. **作業中の `.qgz` プロジェクトを保存し、GeoPackageとともにバックアップ。**
2. 守山区＋周辺の**OSM道路・歩道をベクタとして取得**（XYZタイルとは別）。
3. 歩行可能な道路を選択し、道路接続・通行制限を検証。
4. 病院の位置をネットワークへ接続し、**徒歩10・20・30分の到達可能道路／時間圏**を生成（暫定歩行速度4km/h）。
5. 病院ごとの時間圏と250m人口メッシュを交差し、**元メッシュ面積に対する圏内面積比**で人口を按分。
6. **分析A：** 病院ID×徒歩時間別に、区外住民も含む圏内人口を集計。
7. **分析B：** 同じ時間の全病院の圏域をディゾルブし、守山区でクリップして、区民のアクセス可能人口割合を推計。区外病院も対象に含める。
8. 研究利用時の限界と改善策を、デモの説明資料に記載。

**人口按分の基本式（今後実装）：**

\[
P_{h,t}=\sum_i P_i\frac{\operatorname{Area}(M_i\cap C_{h,t})}{\operatorname{Area}(M_i)}
\]

- \(P_i\)：メッシュ\(i\)の人口
- \(M_i\)：元の250mメッシュ
- \(C_{h,t}\)：病院\(h\)の徒歩\(t\)分圏

この式は**メッシュ内人口の一様分布を仮定した推計**であり、実測された居住位置を表していない。

### 研究者向けに伝える要点

QGISは無料でGUIを備えたGISであり、公開データの重ね合わせ、ネットワーク解析、空間集計、地図作成を一つの環境で試作できる。今回のデモは、分析AとBを同じ基礎データから作ることで、**研究目的の違いが集計方法と解釈を変える**ことを示す。一方、分析処理が成功しても、道路・施設・人口データの品質や方法の妥当性が自動的に保証されるわけではない。

## 7. OSM徒歩道路ネットワークを準備（2026-11-10追記）

### 7.1 QuickOSMで道路を取得

1. QGISの **プラグイン → プラグインの管理とインストール** から `QuickOSM` を導入。
2. **QuickOSM → Quick Query** で次を設定。

   | 項目 | 値 |
   |---|---|
   | Key | `highway` |
   | Value | 空欄（`highway`タグのある地物全般） |
   | 範囲 | `Layer Extent`：守山区＋3kmバッファ `moriyama_buffer_3km` |

3. 取得結果は **Point / Line / Polygon** の3種類に分かれた。今回のネットワーク解析に使うのは **Line**。Point（信号など）・Polygon（道路エリアなど）はひとまず非表示。
4. `Layer Extent` はバッファ形状そのものではなく**外接矩形**。今回は守山区＋周辺3kmより広い道路を取得したが、周辺経路が切れにくい利点もある。
5. Lineの元データを **右クリック → エクスポート → 地物の保存… → GeoPackage** で保存。作業用CRSは `EPSG:6675`。例：`moriyama_osm_roads_raw.gpkg`。

> **留意：** 背景地図のOSM XYZタイルとは異なり、QuickOSMで取得したLineは解析可能なベクタデータ。ただし「地図に道が見える」だけでは経路ネットワークとして正しく接続されているとは限らない。

### 7.2 徒歩で通れると推定される道路を抽出

Line属性に `highway` のほか **`foot` と `access` が存在**することを確認した。`highway=unclassified` は「不明な道路」ではなく一般の地域道路分類であり、原則候補に含める。

**プロセシングツールボックス → 式による抽出（Extract by Expression）**

- 入力レイヤ：`moriyama_osm_roads_raw`
- 出力：`moriyama_osm_walkable_preliminary.gpkg`
- 実際に使った暫定的な抽出方針（次の式）：

```qgis
"highway" IN (
    'residential', 'living_street', 'unclassified',
    'tertiary', 'tertiary_link',
    'secondary', 'secondary_link',
    'primary', 'primary_link',
    'service', 'footway', 'pedestrian', 'path', 'steps'
)
AND (
    "foot" IS NULL OR "foot" NOT IN ('no', 'private')
)
AND (
    "access" IS NULL
    OR "access" NOT IN ('no', 'private')
    OR "foot" IN ('yes', 'designated', 'permissive')
)
```

この式は**デモ用の一次抽出**であり、完全な歩行可否判定ではない。例えば `access=private` と `foot=yes` の併記については後者の明示的な許可を優先する一方、時間帯制限、歩道の有無、階段、未タグ付けの歩行制限などは十分に反映しない。さらに、線が交差していても高架・地下道などで接続されていない場合がある。

**結果：** 抽出後、住宅地・病院周辺の道路が概ね残り、守山区＋周辺の徒歩道路網を表示できた。

### 7.3 対象病院の抽出とテスト施設1件の保存

二つの分析目的のため、範囲の異なる病院レイヤを用意する方針。

| レイヤ例 | 抽出方法 | 主な用途 |

| `moriyama_hospitals_3km` | 病院ポイントを守山区＋3kmバッファで **場所による抽出（intersects）** | 分析B：区外病院を含む区民のアクセス |

※国土数値情報P04などが「病院・診療所・歯科」を含む場合、先に病院の種別コードで抽出する。今回の実際の病院分類コード・施設名は記録されていないため、後でプロジェクトの属性から追記すること。

### 8.4 補間ラスタから徒歩10分圏ポリゴンを作成

QNEAT3の `Output Interpolation` のプロパティで次を確認。

| 項目 | 実測値 |
|---|---|
| CRS | `EPSG:6675` |
| Pixel Size | 約 `10.023 × 10.089 m` |
| NoData | `-9999` |
| Band 1 Min / Max | `18.3801517487` / `731.3012084961` |

```qgis
("Output Interpolation@1" >= 0)
AND ("Output Interpolation@1" <= 666.67)
```

- 実際のレイヤ名は画面の名称に合わせる。
- 入力ラスタと同じCRS、範囲、画素サイズを使って GeoTIFF に保存。例：`moriyama_10min_mask.tif`。
- 条件に合うセルが `1`、合わない有効セルが `0`。**NoDataを1と見なさない**よう確認する。

**(2) プロセシングツールボックス → Polygonize (raster to vector)／ラスタをポリゴン化**

| 項目 | 値 |
|---|---|
| Input layer | `moriyama_10min_mask.tif` |
| Band | `1` |
| Field name | `DN` |
| Output | `moriyama_10min_polygon_raw.gpkg` |


## 9. 徒歩10分圏内人口を面積按分で推計

### 9.1 元の人口メッシュ面積を保存

`moriyama_mesh_local` の属性テーブル → **フィールド計算機**。

| 設定 | 値 |
|---|---|
| 新規フィールド | `mesh_area_m2` |
| フィールド型 | 小数（Real / Decimal） |
| 式 | `$area` |

交差処理の**前に**250mメッシュ全体の面積を保存。CRSの距離単位がメートルであることを確認する。なお、QGISの `$area` はプロジェクトの楕円体面積設定に影響される場合があるため、研究用には**同一の面積算定方法で分子・分母を統一**する。平面面積に統一するなら `area($geometry)` を使って再計算する方法がある。

### 9.2 Intersectionで交差部分の面積に応じて人口を按分

**プロセシングツールボックス → Intersection（交差）**

| 項目 | 値 |
|---|---|
| Input layer | `moriyama_mesh_local`（`population`、`mesh_area_m2` を保持） |
| Overlay layer | **`moriyama_10min_polygon_clean`（`DN=1`のみ）** |
| Output | 例：`moriyama_10min_intersection_corrected.gpkg` |

交差後、フィールド計算機で `pop_est`（小数／Real）を作る。

```qgis
"population" * $area / "mesh_area_m2"
```

これは「各250mメッシュの人口は区画内に均一に分布する」と仮定し、**圏内に入った面積の割合**で人口を配分する方法。実際の居住分布を直接把握しているわけではない。`NULL` の人口を0へ置換せず、値があるセルとないセルを区別する。

### 9.3 Basic statisticsで集計、DN混入により再計算

**プロセシングツールボックス → Basic statistics for fields（フィールドの基本統計量）**

- Input：人口按分済みIntersectionレイヤ
- Field：`pop_est`
- 着目する値：`SUM`（圏内の推計人口合計）

最初の集計時は、Polygonize後に `DN=0` が混在していることを見落としていた。後から二重の境界を調査して判明し、`DN=1`だけのクリーンなポリゴンで**Intersectionから再実行**した。

| 結果 | 修正前（不採用） | 修正後（暫定採用） |
|---|---:|---:|
| Filled（集計した値がある地物数） | 41 | 20 |
| SUM（推計人口） | 6,877.886 | **5,420.89349295857** |
| 四捨五入 | 約6,878人 | **約5,421人** |
| 差 | — | **約1,457人減（約21.2%減）** |

修正後のその他の統計：`COUNT=20`, `UNIQUE=20`, `EMPTY=0`, `FILLED=20`, `MIN≈3.913`, `MAX≈787.339`, `MEAN≈271.045`。

**解釈：** 「テスト病院の徒歩10分圏内人口は、徒歩4km/h・OSM道路網・補間ポリゴン・250mメッシュの面積按分という条件下で**約5,421人と推計**された」。約6,878人は誤った集計範囲を含んだ旧値のため**研究結果に使用しない**。

**検証済みと報告されたこと：** `DN=1`への限定、人口按分値、NULLの確認、重複・人口値の基本チェック。ただし実道路の通行可否、補間面の妥当性、統計の秘匿処理などの独立検証は未実施。

### 9.4 研究者向けデモで強調できること

- **処理が正常に完了しても、そのまま正しい研究指標になるとは限らない。** 今回はDN混入を修正すると推計人口が約21%変化した。
- **GISの幾何学的な妥当性**（Valid判定）と**分析上の妥当性**（正しい圏域・人口・移動条件）は別。
- 線の到達可能範囲を補間して作ったポリゴンは、ネットワーク到達圏の近似であり、面積按分の誤差が生じ得る。
- 再現性のため、OSM取得日、道路抽出式、CRS、移動速度、閾値、ラスタセルサイズ、DNフィルター、面積計算方式を記録する。

### 10.3 全病院の徒歩時間圏を一括計算

**推奨実装：QGIS標準の `Service area (from layer)` と PyQGIS（QGISのPythonコンソール／Processing）を組み合わせる。**

1. 入力：`moriyama_osm_walkable_preliminary` と `moriyama_hospitals_3km`。複数の開始点から到達可能道路をまとめて取得する。`Shortest`（距離）・双方向・トポロジー許容値0を初期条件とする。
2. 30分＝**2,000m**を最大探索範囲とし、10分・20分・30分の区分を**病院IDごとに識別できる形**で作る。標準Service Areaの道路線分はそのままでは病院別・時間別ポリゴンではないため、出力フィールド構造と区分方法を確認する。
3. **病院別ポリゴン化は別工程**。方法を固定してからPyQGISで繰り返す。候補は (a) 到達可能道路への一定幅バッファ＋ディゾルブ（実装しやすいが、厳密な等時間圏ではない）と、(b) QNEAT3補間ラスタを病院単位で生成→各時間閾値で二値化→Polygonize（近似面。QNEAT3自動ポリゴン出力は`contourpy`のコード署名問題で失敗したため回避処理が必要）。**両者は同じ面を返さないので、最終表では方法を混在させない。**
4. まず全病院処理の出力に `hospital_id` と `minutes`（10, 20, 30）が保持される設計にする。各病院×時間について重複面を解消し、幾何学的妥当性と極端に狭い到達圏を点検する。
5. 一括処理が重すぎる場合は病院をバッチに分けて実行し、同じスクリプトで再開できるようにする。**1病院ずつGUIで手動操作する方針には戻さない。**

**留意：** 標準Service Areaで全病院の到達道路を一括取得できても、各病院別の等時間圏ポリゴンが自動的に完成するわけではない。道路の接続性（橋、地下道、交差点）、徒歩通行制限、病院入口へのスナップは依然として未検証。さらに道路線バッファ法は研究用の厳密な徒歩時間面を意味しないので、デモでは「近似」と明示する。

### 10.4 分析A：各病院の時間圏内人口

1. **守山区内の病院**に対応する `hospital_id` の時間圏ポリゴンを利用（人口メッシュは区外も含む）。
2. 病院ID・時間区分ごとにポリゴンを統合して内部重複をなくす。二値マスクからPolygonizeした場合は**`DN=1`のみ**使用し、`DN=0`は除外。
3. `moriyama_mesh_local` と `Intersection`（交差）し、面積按分：`"population" * area($geometry) / "mesh_area_m2"`。**分子・分母の面積測定方法をそろえること**（現行`mesh_area_m2`が`$area`で作られている場合は同じ方法を使うか、元面積フィールドを再計算する）。
4. `hospital_id`・`minutes`別に `pop_est` を合計し、CSVまたはGeoPackageに保存。病院間で同じ住民を重複して数えることは、この**病院別指標では許容**する。

### 10.5 分析B：守山区住民のアクセス率

## 12. 道路到達範囲の30mバッファによるポリゴン化

QNEAT3の自動ポリゴン化はmacOSで `contourpy` のコード署名問題に遭遇したため、本解析では**QGIS標準のBuffer**に切り替えた。これは**等時間圏の厳密な面表現ではない**。あくまで「それぞれの時間以内に到達可能な道路の中心線から30m以内の範囲」という**近似アクセス圏**である。道路からバッファ端までの追加移動時間・建物へのアクセス・障害物は明示的に考慮していない。

**QGIS操作に対応する処理：** プロセシング → ベクタジオメトリ → **Buffer（バッファ）**。実際にはPyQGISで各時間レイヤを連続処理：

```python
import processing
from qgis.core import QgsProject, QgsVectorLayer

p = QgsProject.instance()
line_names = {
    10: 'moriyama_hospitals_10min_lines',
    20: 'moriyama_hospitals_20min_lines',
    30: 'moriyama_all_hospitals_30min_lines',
}
for minutes, name in line_names.items():
    line_layer = p.mapLayersByName(name)[0]
    output = f'{p.homePath()}/access_results/moriyama_hospitals_{minutes}min_buffer30m.gpkg'
    result = processing.run('native:buffer', {
        'INPUT': line_layer,
        'DISTANCE': 30,
        'SEGMENTS': 8,
        'END_CAP_STYLE': 0,
        'JOIN_STYLE': 0,
        'MITER_LIMIT': 2,
        'DISSOLVE': False,
        'OUTPUT': output
    })
    p.addMapLayer(QgsVectorLayer(result['OUTPUT'],
                  f'moriyama_hospitals_{minutes}min_buffer30m', 'ogr'))
```

`DISSOLVE=False` にする理由は**病院ごとの地物・属性を保持するため**。各病院のMultiLineStringの構成線はBuffer処理で統合されたMultiPolygonとして出力された。全病院の圏域を一つに融合するのは後の分析Bだけ。

## 13. 分析A：守山区内8病院の到達圏内人口（完成）

### 13.1 空間集計手順

1. 3つの30mバッファポリゴンレイヤから、守山区内8施設の `fid` を抽出：`3514, 3538, 4117, 4814, 4847, 5822, 6854, 8536`。
2. `moriyama_mesh_local` の250m人口メッシュ（`population`）と病院別ポリゴンを交差させる。実装はPyQGISの `QgsSpatialIndex` で候補メッシュを絞り、`QgsGeometry.intersection()` を使用。GUIなら **Intersection → フィールド計算 → 統計集計** に相当する。
3. 各交差領域の面積比から `population × (交差面積 / 元メッシュ面積)` を合計する。今回のPyQGISでは `geometry().area()` を**分子・分母で統一**して使用。第9節で追加した `mesh_area_m2` フィールドは今回のスクリプトでは直接使わなかった。
4. 人口がNULLのメッシュは0人とみなさず**加算対象外**にし、病院・時間別に件数を記録した。各病院の間で同じ住民が重複して数えられるのは、施設別の圏内人口指標として意図的。
5. 8施設×3累積到達時間＝**24行**をCSV保存。10分≤20分≤30分の人口増加をチェックし、警告なし。

式（メッシュを `i`、対象病院の時間別ポリゴンを `C` とする）：

\[
\widehat{P}_{C}=\sum_{i:\,P_i\,\mathrm{known}} P_i\,\frac{\operatorname{Area}(M_i\cap C)}{\operatorname{Area}(M_i)}
\]

## 14. 分析B：守山区民の「少なくとも1病院への」アクセス率（完成）

**研究上の問い：** 守山区内の住民のうち、守山区内外の対象41病院の**いずれか**について、徒歩10・20・30分以内の近似アクセス圏に入る人口割合は何％か。

### 14.1 実際の処理フロー

入力：`moriyama_boundary`（守山区境界、1 Polygon地物）、`moriyama_mesh_local`、41病院分の3つの30mバッファレイヤ。**すべてEPSG:6675**。

1. 41病院のポリゴンの幾何を **Fix Geometries（`native:fixgeometries`）** で修復。
2. 時間区分ごとに **Dissolve（`native:dissolve`、融合フィールド指定なし）** して、病院間の重複を解消。これにより少なくとも1病院へアクセスできるエリアを一つのMultiPolygon地物として扱う。
3. **Clip（`native:clip`）** で `moriyama_boundary` 内に制限。出力は時間区分ごとに**1地物**だった（内部には複数の面を含み得る）。
4. 守山区内の分母人口：各250mメッシュと行政境界の交差面積割合から推計する。
5. 分子人口：各250mメッシュと、守山区内にクリップした融合済みアクセス圏との交差面積割合から推計する。**分母・分子とも元のメッシュ全面積を分母に用いる**ため、区境をまたぐメッシュも整合的に扱える。
6. `人口アクセス率（%） = 分子÷分母×100`、`圏外推計人口 = 分母−分子`。同じ人口が複数病院の圏域に入っても**1回しか計上しない**。
7. CSVと融合済み範囲のGeoPackageを保存。

```python
import processing

# 「分母」に使う各メッシュの値：
#   population * area(mesh ∩ ward) / area(mesh)
# 「分子」に使う各メッシュの値：
#   population * area(mesh ∩ (union(hospital_buffers) ∩ ward)) / area(mesh)

fixed = processing.run('native:fixgeometries', {
    'INPUT': access_layer, 'OUTPUT': 'memory:'
})['OUTPUT']
dissolved = processing.run('native:dissolve', {
    'INPUT': fixed, 'FIELD': [], 'OUTPUT': 'memory:'
})['OUTPUT']
clipped = processing.run('native:clip', {
    'INPUT': dissolved, 'OVERLAY': boundary,
    'OUTPUT': output_geopackage
})['OUTPUT']
# 以降は交差面積から人数を推計し、分子/分母を算出。
# access_layer, boundary, output_geopackage は各レイヤ/保存先を表す変数。
```

### 17.1 デモで明示する限界

1. **本解析の圏域は正確な徒歩時間ポリゴンではない。** 到達可能道路を徒歩4km/hの経路距離で計算し、その道路に一律30mバッファを掛けた**近似**。バッファ幅の変更で人口推計が変わる可能性が高い。先行テストのQNEAT3補間ラスタ値（約5,421人）と本解析の値は直接比較しない。
2. OSMの徒歩可否属性は暫定ルールで抽出。実際の歩道、通行規制、立体交差、建物入口、信号、勾配、道路データの古さ等は十分に考慮していない。道路網や病院点のスナップの妥当性も独立検証していない。
3. `moriyama_buffer_hospitals` は**守山区＋3km**に立地する41病院に限定。区外の全病院を網羅するものではなく、施設分類・診療機能・受入能力・受診対象者を区別していない。
4. 250m人口メッシュ内の人口が**一様に分布**するとの仮定で面積按分した。建物立地による偏り、NULLや秘匿等による欠損、区境外の人口メッシュ取得範囲の影響を検討する必要がある。
5. **時間間の累積・病院間の重複は別問題。** 分析Aは病院ごとの人口で重複を許容し、分析Bでは41病院の圏域を時間別に融合する。分析Aの人数を足して分析Bの分子にしない。
6. 本指標は**潜在的・地理的な徒歩アクセス**であり、実際の通院行動、診療の可用性、健康アウトカムを示さない。
